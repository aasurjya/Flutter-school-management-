## 1. xAI / Grok agentic capabilities

### 1.1 Function (tool) calling — the request/response contract

The xAI API is OpenAI-compatible. A custom tool declaration requires exactly three mandatory fields: `name`, `description`, and `parameters`, where `name` is a unique identifier ([docs.x.ai/developers/tools/function-calling](https://docs.x.ai/developers/tools/function-calling)). Tool parameters are declared in JSON Schema, supporting `type`, `properties`, a `required` array, `enum` constraints, and `default` values ([function-calling](https://docs.x.ai/developers/tools/function-calling)).

**Tool-count cap — corrected.** The function-calling guide page states a maximum of 200 tools per request, but the authoritative REST API reference (`docs.x.ai/developers/rest-api-reference/inference/chat`) overrides this with **128** for both `POST /v1/chat/completions` ("max of 128 functions") and `POST /v1/responses` ("max of 128 tools"); a May 2026 InfoQ report on the updated Responses API also cites 128. **Use 128 as the working limit; the 200 figure on the guide page is stale.**

`tool_choice` accepts four values: `"auto"` (model decides; default), `"required"` (must invoke at least one tool), `"none"` (tool calling disabled), or a specific function object `{"type": "function", "function": {"name": "..."}}` that forces a named tool ([function-calling](https://docs.x.ai/developers/tools/function-calling)). Parallel tool calls are **enabled by default** — the model can request multiple tool calls in one response — and are disabled with `parallel_tool_calls: false` ([function-calling](https://docs.x.ai/developers/tools/function-calling)).

**Streaming nuance:** when streaming, a function call is returned **whole in a single chunk**, not split across chunks ([function-calling](https://docs.x.ai/developers/tools/function-calling)). *(Medium confidence: this behavior may differ between the Chat Completions API and the newer Responses API, and the docs do not clearly disambiguate.)*

**The tool-use loop — corrected.** A claim circulated that the custom-function loop is exactly four steps ending in a "`tool_result` object." **This is refuted on two points:** the docs describe the cycle as more than four phases, and the wire format is OpenAI-compatible — a message with role `"tool"` carrying a `tool_call_id`, *not* a role/type literally named `tool_result`. The xAI native SDK does expose a `tool_result()` *helper*, which is where the confusion originates, but the helper is an SDK abstraction over the `role: "tool"` message. The correct mental model is the **five-step agentic loop** the overview page documents: (1) analyze the query, (2) decide tool-call vs. direct answer, (3) execute a built-in tool server-side OR return a tool-call request for client-side functions, (4) process results and iterate, (5) return a final response with citations ([docs.x.ai/developers/tools/overview](https://docs.x.ai/developers/tools/overview)). Note this loop is **iterative and multi-turn**, not a single linear pass — the five-step framing is a simplification.

### 1.2 Built-in (server-side) tools

xAI provides **exactly four** built-in server-side tools that run on xAI's infrastructure with no client round-trip: `web_search`, `x_search`, `code_interpreter`, and `collections_search` ([overview](https://docs.x.ai/developers/tools/overview)). They are enabled by adding objects of the form `{ "type": "web_search" }` to the `tools` array ([overview](https://docs.x.ai/developers/tools/overview)). `code_interpreter` executes Python in a sandbox ([overview](https://docs.x.ai/developers/tools/overview)). Responses expose `citations` and `server_side_tool_usage` fields. A May 2026 update added **server-side execution for built-in tools**, which bypasses the client-side loop entirely — relevant because it changes where latency and billing accrue.

> **`x_search` modes — flagged uncertain.** A secondary source describes `x_search` modes including 'Latest', keyword, semantic, user, and thread search ([cobusgreyling Medium](https://cobusgreyling.medium.com/xai-introduced-agentic-server-side-tool-calling-688fb98f450c)). The *capabilities* (keyword/semantic/user/thread) are confirmed by the official x-search docs, but the docs do not enumerate them as a formal `mode` enum, and the older Live Search API (which had explicit mode fields) was retired January 12, 2026. Treat 'Latest' as a likely-but-unconfirmed mode value. For a school app this tool is largely irrelevant — flagged only for completeness.

### 1.3 Remote MCP

The docs page text still restricts MCP to Streaming HTTP/SSE.)* Both `server_url` and `server_label` are listed as required ([remote-mcp](https://docs.x.ai/developers/tools/remote-mcp)) — though the docs' own examples sometimes omit `server_label`, so the page is internally inconsistent. ### 1.5 The dedicated multi-agent model (`grok-4.20-multi-agent`)

xAI ships a purpose-built multi-agent orchestration model, identifier `grok-4.20-multi-agent` (canonical versioned form `grok-4.20-multi-agent-beta-0309`; third parties use `grok-4.20-multi-agent-0309`) ([multi-agent](https://docs.x.ai/developers/model-capabilities/text/multi-agent)). Key mechanics:

- **`agent_count` accepts exactly 4 or 16** — 4 for quick/focused research, 16 for deep/multi-faceted ([multi-agent](https://docs.x.ai/developers/model-capabilities/text/multi-agent)).
- Via the OpenAI SDK, `reasoning.effort` of `"low"`/`"medium"` maps to 4 agents and `"high"`/`"xhigh"` maps to 16 ([multi-agent](https://docs.x.ai/developers/model-capabilities/text/multi-agent)).
- A **designated leader agent synthesizes** the sub-agent discussion and presents the final answer; sub-agent tool calls are **not returned by default** ([multi-agent](https://docs.x.ai/developers/model-capabilities/text/multi-agent)).
- Sub-agent state is encrypted and returned only when `use_encrypted_content` is `True` ([multi-agent](https://docs.x.ai/developers/model-capabilities/text/multi-agent)). *(The Responses API uses the equivalent `include: ["reasoning.encrypted_content"]`; the main purpose is multi-turn context preservation, not just inspection.)*
- **Hard limitations:** no client-side/custom tools, no `max_tokens`, and **not compatible with the OpenAI Chat Completions API** — you must use the xAI native SDK ([multi-agent](https://docs.x.ai/developers/model-capabilities/text/multi-agent)). *(Medium confidence on permanence — the May 2026 release wave is actively changing the landscape; the "Function calling: Yes" on the model detail page refers only to built-in server-side tools, not client-side functions.)*

> **Caution on multi-agent specs.** Five claims sourced from the beta model card — its 1M context window, its 450 RPM / 2.5M TPM rate limit, its $1.25/$0.20/$2.50 pricing, its distinct function-calling/structured-output/reasoning capabilities, and its parallel-agent operation — are all **flagged uncertain**. The beta doc page returns "1M" but the weight of independent evidence (Oracle OCI, OpenRouter, llm-stats, apiyi) points to **2M context**, and OpenRouter/apiyi/llm-stats/puter consistently report **$2.00 input / $6.00 output**, not the model-card figures. ### 1.6 Streaming and SDK

Streaming uses **Server-Sent Events (SSE)** to send content deltas ([streaming](https://docs.x.ai/developers/model-capabilities/text/streaming)), enabled with `stream: true` ([streaming](https://docs.x.ai/developers/model-capabilities/text/streaming)), supported by all text-output models but **not** by image-generation models ([streaming](https://docs.x.ai/developers/model-capabilities/text/streaming)), and terminated with a final `data: [DONE]` event ([streaming](https://docs.x.ai/developers/model-capabilities/text/streaming)). For reasoning models, the docs recommend manually overriding the request timeout (examples use 3600 s) to prevent premature connection closure ([streaming](https://docs.x.ai/developers/model-capabilities/text/streaming)). Each chunk carries `id`, `model`, `created`, and the content delta; **token-usage metadata is NOT in every chunk** — in the default REST/OpenAI-SDK path it appears only in the final chunk and only when `stream_options: {include_usage: true}` is set (claim flagged uncertain/misleadingly-broad as originally stated). The SDK is `pip install xai-sdk` ([PyPI / cobusgreyling](https://cobusgreyling.medium.com/xai-introduced-agentic-server-side-tool-calling-688fb98f450c)); streaming yields `(response, chunk)` tuples where `chunk.tool_calls` exposes `function.name` and `function.arguments` ([cobusgreyling](https://cobusgreyling.medium.com/xai-introduced-agentic-server-side-tool-calling-688fb98f450c)). The response object exposes `server_side_tool_usage` and `citations` alongside `reasoning_tokens`, `completion_tokens`, `prompt_tokens`, and `cached_prompt_text_tokens` ([cobusgreyling](https://cobusgreyling.medium.com/xai-introduced-agentic-server-side-tool-calling-688fb98f450c)).

Third-party guides report per-invocation charges (e.g., web_search and code_execution ~$5/1K calls, collections_search ~$2.50/1K) on top of per-token costs. *(Medium confidence: the official pricing page returned 403 and could not be directly verified; corroboration is from the tool-usage-details page plus third-party sources.)* Each agentic step re-accumulates full conversation history as prompt tokens — a key cost driver for any agentic design.

## 2. Agentic workflow patterns

Anthropic draws the foundational distinction: **workflows** are "systems where LLMs and tools are orchestrated through predefined code paths," while **agents** are "systems where LLMs dynamically direct their own processes and tool usage" ([anthropic.com/research/building-effective-agents](https://www.anthropic.com/research/building-effective-agents)). LangGraph echoes this: agents "use LLMs performing actions via tools in continuous feedback loops" for unpredictable problems; workflows "follow predetermined code paths" ([docs.langchain.com/oss/python/langgraph/workflows-agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)). The patterns below run simplest → most dynamic.

**1. Prompt chaining.** Decompose into sequential steps where each LLM call processes the previous output; the design trades latency for accuracy "by making each LLM call an easier task" ([building-effective-agents](https://www.anthropic.com/research/building-effective-agents)). *Git analogy: a linear commit chain — no branching.*

**2. Routing.** A classifier LLM directs input to one of N specialized prompts/agents. Anthropic's current page illustrates routing easy/common questions to a cheaper model and hard/unusual ones to a more capable model ([building-effective-agents](https://www.anthropic.com/research/building-effective-agents)). *(Uncertain detail: the page names "Claude Haiku 4.5" and "Claude Sonnet 4.5" — anachronistic to the article's Dec 2024 original publication; the pattern is solid, the specific model names were back-edited.)* Tradeoff: classification error poisons the whole path; gains specialization and cost optimization.

**3. Parallelization.** Two variants: **Sectioning** ("breaking a task into independent subtasks run in parallel") and **Voting** ("running the same task multiple times to get diverse outputs") ([building-effective-agents](https://www.anthropic.com/research/building-effective-agents)). Cost multiplies by N; latency is bounded by the slowest branch, not the sum. *Git analogy: short-lived feature branches merged back immediately.*

**4. Orchestrator-workers.** A central LLM **dynamically** decomposes the task at runtime: "unlike parallelization, subtasks aren't predefined — they're determined by the orchestrator based on specific input" ([building-effective-agents](https://www.anthropic.com/research/building-effective-agents)). LangGraph's documented structure: the orchestrator "breaks down tasks into subtasks, delegates subtasks to workers, and synthesizes worker outputs into a final result" ([langgraph](https://docs.langchain.com/oss/python/langgraph/workflows-agents)). Its `Send()` API dynamically creates worker nodes with per-invocation custom inputs ([langgraph](https://docs.langchain.com/oss/python/langgraph/workflows-agents)) — but note worker **inputs** are isolated while **outputs** are written back to a shared state key via a reducer (so isolation is not end-to-end). LangGraph also ships a prebuilt `ToolNode` handling parallel tool execution, error handling, and state injection ([langgraph](https://docs.langchain.com/oss/python/langgraph/workflows-agents)). *Git analogy: a maintainer deciding which branches to open per-subtask.*

**5. Evaluator-optimizer loop.** One LLM creates a response; a second LLM evaluates it; if it needs refinement, feedback is provided and the response is recreated until acceptable ([langgraph](https://docs.langchain.com/oss/python/langgraph/workflows-agents)). Distinct from reflection in that a *separate* model is the critic. Tradeoff: variable latency, infinite-loop risk, cost scales with iteration count.

**6. Reflection.** A single model self-critiques (or checks against tool output) and revises before returning. Empirically, pure self-critique adds little, while **tool-grounded verification** (run the code, query the DB, validate the schema) is the strong variant. *Git analogy: "commit, run CI, amend on failure" — same linear path with repair.*

**7. Branch/merge (fork-explore-commit / tree-of-thought / speculative parallel agents).** The most direct git analog. Forms: tree-of-thought (one agent explores a pruned reasoning tree); speculative/hypothesis forking (N instances each pursue a different continuation; first/best verifiable solution commits, siblings discarded); and multi-agent debate (N agents reason then argue toward convergence — improves factuality but risks sycophancy). Du et al. (2023, [arXiv:2305.14325](https://arxiv.org/abs/2305.14325)) demonstrated that multiple LLM instances proposing then critiquing each other improved factuality and reasoning over single-agent baselines ([zylos](https://zylos.ai/research/2026-03-10-ai-agent-fork-merge-patterns)). FREE-MAD (2025) instructs agents to update beliefs only on clear evidence of being wrong rather than converging socially *(flagged uncertain — a reasonable paraphrase of the paper's anti-conformity spirit, but the actual mechanism is a score-based aggregation function, and the OpenReview submission was later withdrawn)* ([zylos](https://zylos.ai/research/2026-03-10-ai-agent-fork-merge-patterns)).

### The "git-branch-each-idea-then-merge" mental model, concretely

The cleanest formalization is **BranchFS / the "Fork, Explore, Commit" paper** ([arXiv:2602.08199](https://arxiv.org/abs/2602.08199)), which makes the analogy literal at the OS level:

- **Branch = `git checkout -b`.** A "branch context" provides copy-on-write state isolation with independent filesystem views and independent process groups per branch ([arXiv:2602.08199](https://arxiv.org/abs/2602.08199)). Each speculative agent gets its own sandbox.
- **Cheap to fork.** BranchFS achieves branch creation in **under 350 microseconds regardless of base filesystem size** (O(1) creation via copy-on-write) ([arXiv:2602.08199](https://arxiv.org/abs/2602.08199)), and commit overhead stays **under 1 ms for small changes** ([arXiv:2602.08199](https://arxiv.org/abs/2602.08199)) — though commit rises to ~2,100 µs at 1 MB, so "small" matters. It uses **FUSE, requiring no root privileges** ([arXiv:2602.08199](https://arxiv.org/abs/2602.08199)).
- **Merge = first-commit-wins.** The resolution mechanism **automatically invalidates all sibling branches once one branch successfully commits** ([arXiv:2602.08199](https://arxiv.org/abs/2602.08199)) — losing branches are discarded with no effect on "main."
- **Proposed kernel support.** A proposed (currently **unimplemented**) `branch()` Linux syscall would spawn processes directly into isolated branch contexts with kernel-enforced sibling isolation and reliable termination ([arXiv:2602.08199](https://arxiv.org/abs/2602.08199)). *(Flagged uncertain: this is a design proposal only — no kernel implementation exists; the evaluation covers only the FUSE userspace component. Do not present `branch()` as a shipping capability.)*

**How this maps to LLM agents.** Each branch = an isolated speculative agent exploring one idea. The merge = either orchestrator synthesis (LLM-judged), voting, or first-commit-wins. Losing branches are deleted like discarded feature branches. The honest caveat from the field: **forking primitives are strong, merging primitives are weak** — there is no general resolution when branches reach contradictory conclusions, and naive context propagation causes superlinear token growth.

### Cross-cutting evidence on multi-agent behavior

- Anthropic's multi-agent research system achieved a **90.2% performance improvement over a single Claude Opus 4 instance** using parallel subagents with isolated context windows ([zylos](https://zylos.ai/research/2026-03-10-ai-agent-fork-merge-patterns)). *(Nuance: subagents ran Claude Sonnet 4; Opus 4 was only the lead orchestrator. The "3–5 subagents" figure is from third-party summaries, not the exact eval config.)*

- Anthropic, when optimizing their SWE-bench agent, **spent more time optimizing tools than the overall prompt** ([building-effective-agents](https://www.anthropic.com/research/building-effective-agents)) — a strong signal that tool-design quality, not orchestration cleverness, is where returns concentrate.

## 4. Flutter + Supabase LLM integration

**1. Gateway pattern (non-negotiable).** **Never call an LLM from the Flutter client** — any API key in the binary or request headers is extractable. The architecture is **Flutter → Supabase Edge Function → LLM provider**. Keys live in Supabase project secrets (`Deno.env.get('OPENAI_API_KEY')`, set via `supabase secrets set`, never committed). The Edge Function validates the Supabase JWT (`Authorization: Bearer <token>`), enforces per-user rate limiting, and sanitizes the prompt before forwarding. Edge Function cold starts are 120–200 ms; the **hard timeout is 60 s** with a **150 MB memory cap**. For agent loops exceeding 60 s or 150 MB, migrate orchestration to a longer-running tier (AWS Lambda up to 15 min / 10 GB, or a jobs table + `pg_cron` pattern). This directly addresses CLAUDE.md's existing AI text generator at `lib/core/services/ai_text_generator.dart` — orchestration belongs server-side.

**2. Streaming into the Flutter UI.** Use **SSE, not WebSockets**, for unidirectional token streaming. The Edge Function sets `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`, writes `data: <json>\n\n` chunks, and ends with `[DONE]` (matching xAI's own SSE contract from §1.6). On the Flutter side use `http.Client().send(request)` → `StreamedResponse`, pipe through `response.stream.transform(utf8.decoder)`, split on `\n`, and filter lines starting with `data: ` — **critical because multiple SSE events routinely arrive in one TCP packet**. Accumulate tokens in a `StringBuffer` (a `StreamBuilder` snapshot holds only the latest token). **Cancel the `StreamSubscription` in `dispose()`** to avoid leaking server-side connections — this aligns with CLAUDE.md's "real-time channels not cleaned up on dispose can leak" warning. `flutter_ai_toolkit` exposes an `LlmProvider` interface you can point at a custom Edge Function backend.

**3. Server-side tool calling.** Keep the entire tool-calling loop inside the Edge Function: (a) call the LLM with the function-schema payload, (b) on a `tool_use`/`function_call`, execute the real operation (Supabase DB query, external API), (c) append the function response and call again, looping until a final text answer, then stream that text to the client. **The client never sees intermediate tool calls** — only the final answer's tokens. This keeps credentials and business logic server-side. For multi-hop agentic flows exceeding the 60 s timeout, use the jobs-table + `pg_cron` pattern or a longer compute tier. With xAI specifically, the **four built-in server-side tools (§1.2) already keep their execution off the client**, reducing the loop you must hand-write.

**4. Conversational state with Riverpod.** Model conversation state as an **immutable `List<ChatMessage>`** in a `StateNotifier`/`AsyncNotifier`; append by spreading the previous list, **never mutate in place** (matches this project's immutability rule). For streaming, accumulate tokens in a `StringBuffer` and emit `AsyncValue.data([...previousMessages, inProgressMessage])`; **batch UI updates ~every 50 ms** to limit rebuilds during rapid token arrival. Cancel via `ref.onDispose()`; use `ref.keepAlive()` to survive navigation mid-stream. Riverpod 3.0 (Sept 2025) adds `Ref.mounted` — **guard every `state = ...` with it** to avoid setting state on a disposed notifier. Separate the SSE/reconnection client (its own `StreamProvider` or service) from the notifier.

**5. On-device vs cloud.** On-device is viable but niche in 2025–2026 (a 4-bit LLaMA 3 8B runs ~12 tok/s on iPhone 14, ~28 tok/s on Snapdragon 8 Gen 3; ~1.5 GB for a 4-bit 3B model). **For this app — sensitive student data, wide device range, complex reasoning — use cloud LLMs via the Edge Function gateway for all agentic/reasoning tasks**, and reserve on-device only for offline classification (e.g., parent-message sentiment) on high-end devices. The absolute privacy benefit (data never leaves device) is the only reason to revisit this for specific FERPA-sensitive offline tasks.

### 5.1 Single-call vs multi-agent / branch-merge

| Dimension | Single well-prompted call | Multi-agent / branch-merge |
|---|---|---|
| **Quality** | Tran & Kiela (arXiv 2604.02460, Apr 2025): single-agent **0.418 @ 1k tokens, 0.426 @ 10k** on FRAMES/MuSiQue with thinking-tokens held equal — **beat** sequential MAS (0.379 / 0.387). | **Cost** | Baseline (1×). | **~15× tokens** vs chat ([zylos](https://zylos.ai/research/2026-03-10-ai-agent-fork-merge-patterns)); up to **50× variation** across similar-precision systems; token spend explains ~80% of performance variance. | **Reliability** | One failure point; no compounding. | **Error compounding (Lusser's Law):** at 95%/step over 10 steps = 59% pipeline success; 90% = 35%; 85% = 20%. ### 5.2 Evaluation methodology (if you do go multi-agent)

Three layers: (a) **node-level** — tool-selection accuracy, parameter correctness, HTTP error rates (tool-calling accuracy is the dominant production blocker); (b) **session-level** — end-to-end task success, trajectory quality (loop detection), self-aware failure rate; (c) **system efficiency** — latency/step, total token spend, throughput. Agent-as-a-Judge reaches ~90% human alignment vs 60–70% for conventional LLM-as-judge. Define eval sets *before* writing agent code, withhold a test set, and continuously update from production failure logs.

### 5.3 Recommendation: xAI/Grok vs other approaches FOR THIS USE CASE

**Recommended architecture for the school-management app:**

1. **Default to single, well-prompted LLM calls behind the Supabase Edge Function gateway** (§4) for the high-value features in §3 — report-card drafting, parent-communication translation, lesson/quiz generation, and admin NL-Q&A. Anthropic's own guidance: "optimizing single LLM calls with retrieval and in-context examples is usually enough," and the same-compute evidence (Tran & Kiela) shows MAS does not reliably beat a strong single call on closed tasks. **This is the honest anti-over-engineering position: most of this app's AI value needs zero agency.**

2. **Add server-side tool calling (single agent + tools)** only where the model genuinely needs to read live school data (e.g., "how many Grade 8 students are below the fee due date?"). Keep the loop in the Edge Function; validate output schemas; **never** trust hallucinated numbers without surfacing source rows. Tool-calling reliability — not reasoning sophistication — will be your dominant production problem, so invest in tool design over orchestration (mirroring Anthropic's SWE-bench finding).

3. **Reserve branch/merge or the dedicated multi-agent model for, at most, one feature: deep, open-ended research/analysis** (e.g., a district-wide "analyze this cohort's outcomes across three terms" report) where parallel exploration and synthesis genuinely help — and only after it clears the eval bar in §5.2 against the single-call baseline. Budget for ~15× tokens and add validation gates at every handoff.

Error compounding (§5.1) means each added agent multiplies both cost (~15×) and failure surface (up to 17.2× error amplification when uncoordinated). Add agency only when a measured eval shows it beats the single-call baseline on your own data. Architecture should match business value, not technical ambition.

## 3. The highly-agentic flow (server-side BRANCH/MERGE in `ai-gateway`)

### 3.1 The git metaphor, mapped to named patterns

The branch/merge mental model maps cleanly onto two verified agentic patterns from Anthropic's *Building Effective Agents* and LangGraph's workflow docs:

- **BRANCH = orchestrator-workers.** A central orchestrator LLM call **dynamically** decides which specialist sub-tasks to spawn based on the specific request — "unlike parallelization, subtasks aren't predefined" (Anthropic, supported). This is `git checkout -b`: each branch is an isolated worker with its own context window. Anthropic's own multi-agent research system got **90.2% improvement over a single Claude Opus instance** using 3-5 parallel subagents with **isolated context windows** (supported) — this is the empirical case for fan-out, and the isolated-context point is exactly the `git worktree` analogy.
- **MERGE = evaluator-optimizer.** One LLM call generates candidates; a second evaluates against success criteria and either accepts or sends feedback for another round (LangGraph, supported). This is `git merge` with a review gate — the evaluator is the reviewer who approves the best branch or requests changes.

Two research-grounded refinements:
- For **candidate drafts of the *same* task** (e.g. 3 report-card remark styles), use **Voting** — "running the same task multiple times to get diverse outputs" (Anthropic, supported) — then merge by evaluator selection. This is the `git merge --strategy=ours` after comparing branches.
- The **first-commit-wins** discipline from BranchFS (arXiv:2602.08199, supported) maps to our idempotency gate: once one branch's result is committed to `tenant_ai_usage` under the idempotency key, sibling retries are deduplicated — we already have this invariant (`index.ts:148-157`); the agentic layer must preserve it.

### 3.2 Cost discipline (research-gated — "don't over-agent")

Multi-agent fan-out costs **~15× more tokens than single chat** (Anthropic, supported) and communication grows **O(n²)** with agent count (supported, mathematically sound). Therefore the orchestrator must **gate on task complexity** before branching — most requests stay single-shot. The verified failure-mode stats ("40% of pilots fail", "40-60% cost savings") are *uncertain/unattributed marketing* in the research and must **not** be used to justify the architecture; the defensible claims are the 15× token multiplier, O(n²) coordination cost, and the 90.2% quality lift. Net: branch only when the quality lift is worth the 15× — i.e. high-stakes, low-volume tasks (report-card batches, timetable optimization), never per-keystroke chat.

### 3.4 Tool/function calling under tenant RLS (the safety crux)

The model must read attendance, marks, and fees **without ever choosing the tenant**. The pattern:

1. **`tenant_id` comes from the JWT, never from the tool arguments.** The orchestrator extracts it once (`index.ts:122`) and every tool execution appends `.eq('tenant_id', tenantId)` server-side. The model's tool args carry only intra-tenant selectors (`student_id`, `section_id`, `date_range`) — it physically cannot widen scope.
2. **Tools are a fixed, audited catalog per feature_route** — `get_attendance_summary(section_id, range)`, `get_marks(student_id, exam_id)`, `get_fee_status(student_id)`. Parallel tool calls are fine (xAI: parallel calls on by default; supported) and welcome since reads are independent — but the catalog is allow-listed, so the model can call only what the route declares.
3. **Read-only enforcement is structural, not prompted** — the service-role client used in tool execution is wrapped so only `SELECT`-shaped helpers are reachable; there is no write tool. This is the dedicated-tool-over-bash principle from Anthropic's agent-design guidance (typed, gateable hooks vs. an opaque command string).
4. **Streaming note:** with OpenRouter/xAI streaming, a function call returns whole in a single chunk, not split across chunks (xAI, supported) — so the gateway buffers tool-call chunks fully before executing, then resumes the SSE stream to the client (matching the `data: [DONE]` SSE discipline already implicit in the OpenAI-compatible path).

- The "lowest hallucination rate" marketing claim is *uncertain* — don't lean on it; keep the §5 hallucination guardrails regardless of provider.
- Streaming timeout: for reasoning-heavy agentic turns, xAI docs recommend overriding the request timeout (supported) — set a generous timeout on the gateway's fetch to Grok, mirroring the long-turn streaming guidance.

## 5. Guardrails

- **Tenant isolation (hard boundary).** `tenant_id` is read from the JWT only (`index.ts:122`); every tool read appends `.eq('tenant_id', tenantId)` server-side; tool args never carry a tenant selector. No write tools exist in the catalog — the agent is structurally read-only. This is the same RLS invariant the rest of the app depends on, enforced at the one place (the gateway) that holds `service_role`.
- **Budget + idempotency governance (already built — extend, don't replace).** Keep the daily quota gate (`index.ts:181-195`) and the `(tenant_id, idempotency_key)` dedup (`index.ts:148-157`). Critically: an agentic request fans out to N+2 model calls (orchestrator + N workers + evaluator), so **count every branch against the budget** and log each to `tenant_ai_usage` — otherwise one agentic call silently costs 15× a chat call (verified token multiplier) and blows the cap. The idempotency key covers the **whole** agentic request (first-commit-wins): a retry returns the merged result, never re-runs the fan-out.
- **Hallucination / PII handling.** (a) The evaluator step *is* a hallucination gate — its rubric must include "every factual claim is grounded in a tool result," echoing the Fable-5 grounding guidance ("audit each claim against a tool result; only report work you can point to evidence for"). (b) Tool reads return only the columns the feature needs — no raw PII dumps into the prompt; fee/health data is fetched per-student, not per-section. (c) Provider hallucination claims are unverified across the board, so the grounding gate is provider-independent.
- **"Don't over-agent" gates (research-mandated).** The orchestrator branches **only** when complexity warrants it — default to single-shot. Caps: `branch_cap ≤ 3` per route (Anthropic's effective range is 3-5; we stay conservative given free-tier models), **max 1 evaluator-revision round**, and a hard tool-call ceiling per branch. Rationale is the verified 15× token cost and O(n²) coordination growth — not the unattributed "40% fail" stat. Per-keystroke chat (the FAB, #5) stays single-shot with at most a few tool reads; batch/high-stakes tasks (#6, #10) are the only ones allowed to fan out.
